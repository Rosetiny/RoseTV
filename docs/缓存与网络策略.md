# 缓存与网络策略

| 数据 | 复用和上限 |
| --- | --- |
| 前端接口结果 | 5 分钟；最多 80 项、约 4 MiB 内存 |
| 后端公开目录快照 | 6 小时；最多 512 项、8 MiB 序列化内容，压缩保存 |
| 单片稳定资料 | 最长 30 天；与目录共用总容量上限 |
| 前端影片资料 | 最多 600 条、512 KiB；30 天淘汰 |
| 海报与网络内容 | 使用 WebView2 有上限的 HTTP 缓存；目标预算 32 MiB |
| 收藏 | 最多 200 部 |
| 登录浏览器档案 | 独立统计，不属于可随意清除的片单缓存 |

启动不是整库重新抓取。已保存且有效的资料先读取本地，没有命中时才请求。对方提供 ETag / Last-Modified 时使用标准缓存验证；不能凭空判断从未返回过的数据是否发生变化。

## 分页与预读

桌面默认每页 16 部。已有 32 条快照继续复用；新批次请求 `count=64`，正常可供约四页复用。实际返回数量和非影片卡片由上游决定；这不是豆瓣所有页面统一的批量大小。即使上游实际只返回较小批次，分页也会按真实游标继续。

原始批次与界面页码分开计数。榜单卡片、重复影片被略过后，下一批中有效影片连续补齐前一页；读取过的批次及页游标都会保存。只有片库末页允许少于 16 部。直接跳到从未访问的很远页码，需要先建立连续游标，首次可能等待；不会捏造数据来填满。

当前页提交后，空闲时准备后两页，不链式预读整库。后台请求优先级低于当前点击，保留前台请求额度。网站限制期间停止预读；取消旧查询时释放排队任务。

## 海报传输

可见海报最多 4 个前台请求，后台预热串行 1 个。使用浏览器缓存；翻页终止旧图片请求并清除对应 Blob URL。单张海报请求有超时及手动重试。已完成的海报缓存供后续显示复用，不保存无限图片副本。

## 限制的含义

豆瓣本机策略是 1 个活动请求、间隔至少 4 秒、每分钟最多 8 次；账号网站至少间隔 2 秒、每分钟最多 12 次。它们是应用主动保守设置的预算，不是对方公开保证的封禁阈值。

遇到真实 HTTP 403/429、验证页或登录要求时暂停请求，并考虑 Retry-After。提高本机预算不能保证上游允许，切换备用网址也不用于绕过限制。交叉筛选压力检查主要在本地响应上执行，真实网站只做有限抽样。
